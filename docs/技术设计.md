## 2. 总体架构

单模块 `:app`，按层分包（v1 不拆多模块，个人项目优先务实，未来可平滑拆 feature 模块）：

```
UI 层（Compose Screens + ViewModels）
        │  StateFlow / 事件
Domain 层（model / repository 接口 / usecase）
        │
Data 层（Room DAO + Repo 实现 / Retrofit AI / DataStore / 备份）
```

**关键设计决策（对齐 PRD §13 一致性规则）：**

1. **营养字段一律 `nullable`**，缺失≠0，UI 显示「未知/—」而非 0。
2. **手动覆盖与明细合计互斥**：餐次 `totalCaloriesOverride` 为空则取明细合计，二者不叠加。
3. **草稿用 `status=DRAFT` 标记**，统计查询只取 `SAVED`。
4. **热量目标带 `effectiveDate`**，历史按当日目标回显。
5. **食物明细直接落解析后的营养值 = 使用时的快照**，营养库更新不回溯修改历史。
6. **AI 识别结果进入「待确认」态**，用户确认后才落库，不静默覆盖人工修改。
7. **全部正式记录用 UUID 主键**，复制生成新 UUID。
8. **实体即领域模型（单模块务实取舍）**：v1 不引入独立领域数据类与映射层，Room Entity 直接作为 Repository 接口的返回类型（`domain/repository` 返回 `data` 层 entity）；枚举与纯值对象（如 `NutritionSummary`）放 `domain/model`。未来拆多模块再引入 DTO/mapper。

## 4. 数据库方案（Room，7 张表）

> **阶段 1 修订摘要**（相对 V1.0 设计，最终落库结构见下）：
> 1. 新增 `DayCompletenessEntity`：把「记录完整度」从 MealRecord 拆出。完整度是「按天」属性（PRD §9「用户可将某天标记为完整/可能不完整」、§10.3），放进单条餐次会导致一餐一个完整度值的语义冲突。
> 2. `MealRecord` 增加 `name` 字段：支持快速模式仅凭「名称 + 总热量」保存记录（PRD §4.2）。
> 3. `FoodDb` 增加 `sourceId` 字段：来源条目可追溯（PRD §5.1「数据来源与版本」）。
> 4. `WeightRecord` 以 `date` 为主键，替代「id + date 唯一索引」：每日期一条是自然键，`@Upsert` 按主键去重正好实现「同一天覆盖、不同天新增」。
> 5. 阶段 1 已落地：7 个 DAO、6 个 Repository（接口 + 实现）、`NutritionCalculator` 营养规则、USDA 种子数据；`exportSchema` 已启用并将 schema JSON 纳入版本控制。
> 6. 阶段 2A 已落地：为支持「快速模式仅凭名称 + 总热量 + 可选营养」保存（PRD §4.2），`MealRecord` 增加餐次级营养覆盖 `proteinOverride`/`carbsOverride`/`fatOverride`（可空 REAL），数据库 v1 → v2（追加式 `MIGRATION_1_2`，见 §4.10）。首页改为读取真实今日数据，记录模块实现文字录入 → 统一确认 → 保存/草稿。

### 4.8 DataStore（非 Room 表）

- **Settings**：主题模式、提醒开关与各餐/总结时间、个人信息（年龄/身高/体重/活动水平/性别，供自动估算目标）。
- **ApiConfig（非敏感部分）**：Base URL、视觉模型 ID、文本模型 ID。
- **API Key** 单独入 Keystore/EncryptedSharedPreferences，不落 DataStore、不进备份。

### 4.9 一致性规则落库映射（PRD §13）

| 规则 | 落库方式 |
|---|---|
| 缺失≠0 | 全部营养列可空 |
| 覆盖优先、不重复叠加 | `totalCaloriesOverride` 与明细合计互斥取一（`NutritionCalculator.mealCalories`） |
| 草稿不统计 | `status` 过滤 |
| 目标按生效日期 | `CalorieGoal.effectiveDate` + `getEffectiveOn(date)` |
| 历史快照不可变 | 明细直接落解析值 + `foodDbId`/`foodDbVersion`/`sourceId` 追溯 |
| 复制新记录 | 每次复制新 UUID |
| 记录完整度按天 | `DayCompleteness.date`（与餐次分离） |
| 未记录≠进食 | 无记录日期不生成统计行，`NutritionSummary` 全字段 null |

### 4.10 TypeConverter、迁移与系统备份

- **类型转换**：`LocalDate`/`LocalTime` 用 TypeConverter 存 ISO 字符串；枚举由 Room 默认以 `name()` 字符串落库（只允许追加常量、禁止重命名已有常量）。
- **迁移**：`exportSchema = true` + `room.schemaLocation` 已配置，schema JSON（`app/schemas/`）纳入版本控制。当前 `version = 2`。`Migrations.MIGRATION_1_2` 为追加式迁移：向 `meal_records` 新增 `proteinOverride`/`carbsOverride`/`fatOverride` 三列（可空 REAL），历史记录这三列保持 NULL（缺失 ≠ 0），已通过 `addMigrations(...)` 注册到 `DatabaseModule`；**不使用** `fallbackToDestructiveMigration`。未来升级需按 schema 差异编写 `Migration` 并注册，避免真实用户数据因升级丢失。
- **系统备份（Android Auto Backup）**：保留 `allowBackup=true`（Room DB 随系统备份，利于换机/重装保留数据），但通过 `dataExtractionRules` + `fullBackupContent` 排除 `secure_api_config.xml`。该文件将存放 Keystore 加密的 API Key；Keystore 密钥无法随备份迁移，若被备份会导致恢复后无法解密（阶段 3 实现时落地）。

## 5. 关键模块设计要点

**AI 模块**：Retrofit 调用 `POST {baseUrl}/chat/completions`（OpenAI Chat Completions 风格）。文字模型做食物解析、视觉模型做图片识别（图片以 `image_url` + base64 data URL 传入）。文本/视觉各自独立连接测试。异常（额度/限流/超时/解析失败）→ 保留草稿 + 手动入口 + 可重试，不自动重复付费请求。

**照片**：存 `filesDir/photos/`，DB 存相对路径；上传前剥离 EXIF 元数据；首页/历史用 Coil 加载。

**备份/恢复**：业务数据序列化 JSON + 照片文件 → 打包 zip；可选 PBKDF2+AES-GCM 加密（含盐/迭代/认证码检测篡改）。备份内嵌 manifest（版本、时间、校验和）。恢复先校验 → 展示概要 → 确认后事务替换，失败不破坏现有数据；**不恢复 API Key**。

**CSV 导出**：饮食记录 + 食物明细 + 热量营养 + 体重 + 日期/餐次/来源。

**提醒**：AlarmManager 本地通知；当日已有对应餐次 SAVED 记录则跳过；未授权通知时明确提示不影响其他功能。

## 6.1 阶段 2A 修复记录（真机验收）

针对阶段 2A 真机验收发现的三类问题，在不改 schema、不做破坏性迁移、不清理既有数据的前提下修复：

1. **草稿无法恢复**：记录页「未完成草稿」入口读取真实 `observeDrafts()`（按 `updatedAt` 倒序）展示草稿数量与列表（名称/日期/餐次/更新时间/热量）。点击恢复表单，支持编辑/再保存/删除（删除二次确认）。转正式与再次保存草稿均复用原 UUID——`RecordViewModel` 用 `editingId`/`editingCreatedAt` 记忆原记录，`@Upsert` 按主键去重，`DRAFT → SAVED` 仅更新 `status`，不产生重复记录；`createdAt` 保留、`updatedAt` 刷新。支持仅名称无热量的部分草稿。

2. **保存后不能立即返回首页**：根因是 `SnackbarHostState.showSnackbar` 为挂起函数，此前在 `RecordScreen` 内 await 后再导航会阻塞返回。修复为将 `SnackbarHost` 提升到 App 级 `Scaffold` 并用 App 级 `rememberCoroutineScope` 弹提示，`Saved` 事件先 `onNavigateHome()` 立即返回、再异步 `onShowMessage`，二者解耦。保存期间 `isSaving` 驱动「保存中…」禁用按钮 + `if (_isSaving.value) return` 防重入；保存失败保留表单与脏标记、不导航；事件用 `MutableSharedFlow.tryEmit` 避免页面销毁导致的协程泄漏。

3. **统一退出保护**：顶部返回、系统返回键、底部导航切换三种离开方式统一走放弃确认。新增 `isDirty`（区别于 `hasContent`，精确表达「有未保存修改」）；脏标记经 `onDirtyChange` 提升到 App 层（`recordDirty`/`pendingNavigation`），底部导航在离开脏记录页时先挂起待导航、由 `RecordScreen` 统一弹「放弃修改？」对话框，确认后先 `backToEntries()` 重置 ViewModel 再 `onDiscardResolved(true)` 导航，避免返回时残留旧状态。

**测试**：`RecordViewModelTest`（草稿恢复/保存新草稿/转正式复用 UUID 并保留 createdAt/再保存复用 UUID/保存失败保留表单/删除草稿）+ `MealRecordDaoTest` 与 `MealRecordDaoInstrumentedTest`（`observeDrafts` 过滤与倒序、草稿转正式复用 id 不重复、删除草稿不影响其他记录）。

## 6.2 阶段 2B 记录（详细输入 + 本地营养计算）

在不改 schema、不做破坏性迁移、不清除既有数据的前提下，为文字记录补齐「详细输入」模式与本地营养库折算：

1. **双输入模式**：记录页「文字记录」入口弹出选择对话框，提供「快速输入」（沿用阶段 2A 的名称 + 总热量 + 可选营养）与「详细输入」（逐条食物明细）。`RecordViewModel` 新增 `InputMode`（QUICK/DETAIL），快速模式 `source=MANUAL_QUICK`，详细模式 `source=MANUAL_DETAIL`。

2. **详细模式明细增删改**：详细表单内可「添加食物」「编辑」「删除」明细。每条明细记录名称、分类、重量(g)、快照营养值（热量/蛋白/碳水/脂肪，均可空）、来源（`FoodSource.LOCAL_DB`/`MANUAL`）与 `foodDbId`/`foodDbVersion`。

3. **本地库搜索**：`FoodDbDao.search` 增加 `category` LIKE 匹配，支持按中文名称/别名/分类搜索；搜索页提供「全部/生/熟」`RawCooked` 筛选与每 100g 参考值展示。

4. **按克折算**：选择本地库食物后输入克数，`NutritionCalculator.computeFromFood` 按每 100g 折算四项营养并实时预览；食物编辑页对非本地库食物支持手动录入名称/重量/可选营养（缺失保持 null，不默认 0）。

5. **汇总与覆盖**：详细表单实时展示「明细合计」；可选「总热量覆盖」字段，填写后写入 `totalCaloriesOverride`，统计时优先于明细合计、不重复相加（复用 `NutritionCalculator.mealCalories` 既有互斥逻辑）。

6. **营养快照**：明细落库时直接保存折算/手填的营养值 + `foodDbId`/`foodDbVersion`，本地营养库更新不回溯修改历史记录（新增 `MealRepositoryImplTest.营养快照不随本地库更新改变` 覆盖）。

7. **草稿/退出保护回归**：详细草稿连同明细一起恢复（`openDraft` 改读 `getMealWithItems`）；保存、立即返回首页、统一退出保护沿用阶段 2A 修复，未回退。

**来源核验说明**（PRD §5.1「来源与版本」诚实性约束）：

- 12 条示例食物沿用 USDA FoodData Central 常见参考值；已抽查核验「鸡胸肉（生，去皮，120 kcal / 22.5g 蛋白 / 2.6g 脂肪）」与「北豆腐」数量级与 USDA 一致。
- `sourceId` 由原先的占位字符串 `usda-fdc:<id>` 改为 **null**，避免被误认为真实 USDA FDC 条目 ID；`source` 字符串改为「USDA FoodData Central 常见参考值（示例，待核对官方 FDC 条目 ID）」。
- 「北豆腐（硬）」为中式豆制品，无单一 USDA FDC 条目直接对应，数值为常见参考值，不视为精确测量值。
- 种子仅 `onCreate` 写入，已安装设备不改动既有 `food_db` 行（符合「不做破坏性迁移、不清除数据」）。

**测试**：

- 单元（Robolectric/纯 JVM，共 52 个通过）：`RecordViewModelTest` 新增详细模式（手动新增/本地库折算快照/删除重算/覆盖优先/缺失 null/草稿恢复/无食物不可确认/克数非法不可添加）；`FoodDbDaoTest` 新增按分类搜索；`MealRepositoryImplTest` 新增营养快照不变。
- 仪器化（已编译通过，待真机）：`FoodItemDaoInstrumentedTest`（明细写入/读取/重启持久化）。
- 阶段 2A 快速录入回归测试全部保留并通过。

## 6.3 阶段 2C 记录（照片记录 + 本地图片管理）

在不改 schema、不做破坏性迁移、不清除既有数据的前提下，为记录补齐「照片记录」能力并做好本地图片生命周期管理：

1. **拍照记录入口**：记录页「拍照记录」入口启用，复用 `ActivityResultContracts.TakePicture` + FileProvider（应用不声明 CAMERA 权限）；「相册选图」复用 `ActivityResultContracts.PickVisualMedia` + `PickVisualMediaRequest(ImageOnly)`（不声明 READ 权限）。二者均由系统代理授权，符合 PRD 权限最小化。

2. **照片私有化存储**：新增 `PhotoRepository`（`savePhoto/deletePhoto/resolve/listPhotos`）与其实现 `PhotoRepositoryImpl`。照片复制到 `filesDir/photos/<uuid>.jpg`，返回相对路径 `photos/<uuid>.jpg` 存入 `MealRecordEntity.photoUri`（复用既有可空列，DB 仍为 v2，无 schema 变更）。

3. **照片展示**：新增 `PhotoThumbnail` 组件，用 `produceState` + `Dispatchers.IO` + `BitmapFactory` 降采样（目标 512px）异步加载，无 Coil 依赖；照片缺失/失效时显示「无照片」占位。编辑表单、确认页与首页餐次卡片均接入。

4. **与手动记录结合**：快速/详细手动记录均可附加照片，`MealFormState.photoUri` 纳入 `hasContent` 判断，`buildMeal` 两条分支均写入 `photoUri`。不依赖 AI。

5. **已保存餐次照片查看/更换/移除**：`RecordViewModel` 用 `editingOriginalPhotoUri` 区分「会话新建」与「已入库」照片；更换时清理旧文件、移除时清理本次文件，避免误删仍在引用中的照片。

6. **草稿照片持久化**：`toFormState` 回填 `photoUri`，草稿连同照片相对路径落库，重启后 `openDraft` 仍可恢复。

7. **无主文件清理**：`MealRecordDao.getAllPhotoUris()` 读取全部已引用相对路径，`MealRepositoryImpl.deleteOrphanedPhotos()` 对比 `photos/` 目录与引用集合，仅删除无主文件。`deleteMeal` 在事务后连带删除该记录的照片文件。

**测试**：

- 单元（Robolectric/纯 JVM，共 68 个通过）：`RecordViewModelTest` 新增 8 条照片用例（拍照保存含照片路径、相册选图落私有目录并挂表单、移除删本次文件、更换删旧未保存文件、编辑更换保存后清理旧照片、丢弃表单删未保存照片、草稿保留照片路径、打开带照片草稿恢复）；`MealRepositoryImplTest` 新增 2 条（删除餐次连带删照片、清理无主照片且不删被引用照片）；`HomeViewModelTest` 补齐 `deleteOrphanedPhotos` 桩。
- 仪器化（真机 PLB110，共 15 个通过）：`MealRepositoryInstrumentedTest` 含照片生命周期路径。
- 阶段 2A/2B 记录、编辑、删除、草稿回归测试全部保留并通过。
