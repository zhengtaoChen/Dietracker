# AI 饮食记录与热量管理 App
## 产品需求文档 PRD V1.0（定稿候选）

**目标平台：** Android  
**产品类型：** 个人饮食记录与热量管理工具  
**数据模式：** 本地优先，未来可扩展云端同步  
**当前阶段：** 功能与交互需求确认

---

## 1. 产品定位与目标

开发一款简单、实用、以 AI 为辅助的 Android 饮食管理软件。

### 1.1 核心目标

1. 快速记录每日饮食，支持拍照、文字和快捷复用。
2. 通过 AI 或本地营养数据库估算热量和三大营养素。
3. 即使 AI API 不可用，也能完整使用基本功能。
4. 设置并管理每日热量目标。
5. 通过图表观察饮食及体重的长期变化。
6. 让用户始终能够管理、备份和导出自己的数据。

### 1.2 产品设计原则

- 记录优先，AI 辅助。
- 尽量减少日常操作步骤。
- 用户输入优先于 AI 估算。
- 不将未知营养数据默认为零。
- 不把未记录饮食理解为没有摄入。
- 不以连续打卡或负面评分增加使用压力。
- 不依赖账号、云端服务器才能使用基本功能。

## 2. 系统平台与总体结构

### 2.1 平台

仅支持 Android，不在第一版开发 iOS。

第一版主要面向个人使用，采用本地数据存储，不需要注册登录。

### 2.2 底部导航

固定四个主要入口：

| 页面 | 主要职责 |
|---|---|
| 首页 | 今日热量、营养目标及餐次概览 |
| 记录 | 拍照、文字、快捷记录及手动输入 |
| 历史 | 日历、记录详情、编辑与删除 |
| 统计 | 热量、三大营养素和体重趋势 |

设置页面通过首页右上角进入。

### 2.3 视觉风格

采用极简数据风格与温暖生活风格结合的设计：

- 默认浅色主题，支持深色和跟随系统。
- 白色或暖白色背景。
- 蓝绿色作为主要强调色。
- 使用圆角卡片、清晰的进度条和简洁图表。
- 饮食历史突出照片，首页和统计页突出数据。
- 避免复杂动画与不必要的页面跳转。

## 3. 首次启动流程

首次安装后展示轻量引导：

1. 欢迎与功能介绍。
2. 个人信息与每日热量目标设置。
3. AI API 配置。
4. 进入首页。

每一步均允许跳过。

不要求注册账号，不要求首次启动时配置 API。

尚未设置目标时，首页只展示已记录摄入量，不显示虚构的目标值或剩余额度。

相机、图片访问与通知权限在实际使用相关功能时申请。

## 4. 饮食记录模块

### 4.1 三种平等入口

**拍照记录**

- 支持直接拍照与选择相册图片。
- 可以附加文字描述。
- 支持 AI 图片识别。
- 支持跳过 AI，直接填写热量。
- 照片与饮食记录关联保存在本地。

**文字记录**

- 可输入自然语言，让 AI 解析食物。
- 也可以完全跳过 AI，直接手动记录。
- 支持快速输入和详细输入。

**快捷记录**

- 复制历史餐次。
- 从收藏的常吃食物中选择。
- 修改份量、时间和热量后保存。

### 4.2 手动输入的两种模式

**快速模式**

至少需要食物或餐次名称、总热量。

其他信息可选，包括照片、具体食物、蛋白质、碳水、脂肪和备注。

支持直接输入外部 AI 给出的热量结果。

**详细模式**

支持添加多条食物明细，每条可包含：

- 食物名称。
- 食物重量或份量。
- 热量。
- 蛋白质。
- 碳水化合物。
- 脂肪。
- 食物数据来源。

没有营养信息的字段保留未知状态。

### 4.3 统一确认页面

所有记录入口最终进入统一的编辑和确认页面。

展示日期、时间、餐次、照片、食物明细、总热量、营养素及备注。

支持增加、删除和修改食物。

保存后立即更新首页、历史和统计数据。

### 4.4 手动热量覆盖

系统同时保留：

- 根据食物明细计算的热量。
- 用户手动覆盖的总热量。

当用户主动覆盖总热量时，以用户数值参与统计，不重复叠加。

如果用户随后编辑食物明细，系统不能静默覆盖手动值。应展示重新计算结果，让用户选择继续保留手动值或采用明细计算值。

### 4.5 草稿

AI 请求失败、网络异常或编辑中断时，保留未完成记录。

草稿不能参与正式的每日摄入量统计。

草稿可重新打开、编辑、分析、保存或删除。

## 5. 本地食物营养数据库

第一版内置常见基础食物的营养数据。

建议初始规模为约 150–300 种，最终数量由可合法使用且经过校验的数据决定。

### 5.1 数据范围

包括主食、肉类、蛋奶豆制品、蔬菜、水果、油脂与部分常见熟食。

每条基础食物至少记录：

- 食物名称与类别。
- 每 100g 热量。
- 每 100g 蛋白质、碳水、脂肪。
- 生熟状态。
- 数据来源和版本。
- 可用别名。

### 5.2 使用方式

用户搜索并选择食物后，输入重量即可计算营养值。

对于无法可靠匹配的食物，允许直接填写估算结果。

本地数据库支持用户新增、修改和收藏自定义食物。

营养数据库更新不能静默修改历史餐次已经确认的热量；历史记录应保存使用时的营养数据快照。

## 6. AI 服务模块

### 6.1 用户自行配置

支持填写：

- API Base URL。
- API Key。
- 视觉模型 ID。
- 文本模型 ID。

视觉模型与文本模型可以不同。

第一版优先兼容经验证的 OpenAI Chat Completions 风格接口，不承诺兼容所有第三方服务。

### 6.2 连接测试

分别提供文本模型测试和视觉模型测试。

用户能够看到连接成功、认证失败、额度不足、频率限制、模型能力不匹配以及网络异常等结果。

### 6.3 AI 食物识别

AI 尝试识别食物种类、估算份量与烹饪方式。

对于匹配可靠的食物，优先采用本地营养数据库计算。

对于复杂菜肴，允许保留 AI 估算值。

识别结果均可由用户修改。

### 6.4 基础营养评价

提供每日及近 7 天的营养概览、目标差异与数据完整度提示。

优先通过本地统计规则完成分析。

可选的自然语言总结由用户主动触发，不进行后台自动调用。

不开发下一餐推荐、食谱生成或连续对话式 AI 助手。

### 6.5 API 异常处理

当 API 额度不足、限流、网络超时或解析失败时：

- 保留已有输入和照片。
- 提供手动填写入口。
- 允许保存草稿。
- 允许用户稍后主动重试。
- 不自动重复发送付费请求。
- 不覆盖用户已经确认的营养数据。

### 6.6 安全与隐私

API Key 使用 Android 安全存储机制保护。

不在程序中内置开发者私有 API Key。

默认使用 HTTPS。

只有用户主动发起分析时，才向配置的模型服务发送必要图片或文本。图片上传前应尽可能移除不必要的位置等元数据。

## 7. 每日热量目标

支持三种方式：

1. 自动估算。
2. 手动设置。
3. 跳过设置。

自动估算结合用户自愿提供的年龄、身高、体重、活动水平、适用的计算参数和体重管理目标。

支持减脂、维持体重、增重。

估算结果仅作为参考，用户可以随时调整。

保存目标的生效日期，历史统计按当时的目标展示。

热量目标与剩余摄入额度不能被表述为已经测量得到的真实能量缺口。

---

## 8. 首页

从上到下展示：

1. 当前日期与设置入口。
2. 今日已记录热量、目标与剩余额度。
3. 蛋白质、碳水、脂肪摄入信息。
4. 今日餐次列表和照片。
5. 快速添加饮食按钮。

当部分餐次缺少营养信息时，显示已知摄入值及数据不完整标记。

当没有照片时使用简洁的默认图标。

无记录时展示友好的空白页面和记录入口。

---

## 9. 历史记录

以月历作为默认入口。

点击日期查看对应餐次，包括时间、照片、名称、热量和营养信息。

支持：

- 查看详情。
- 修改记录。
- 删除记录。
- 复制到其他日期。
- 收藏常吃食物或餐次。
- 补录过去的饮食。

用户可将某天标记为记录完整或记录可能不完整。

未记录日期不视为摄入零热量。

---

## 10. 统计分析

### 10.1 热量趋势

支持近 7 天与近 30 天的视图。

展示每日已记录摄入量、当日目标以及有数据日期的平均摄入量。

### 10.2 三大营养素

展示蛋白质、碳水和脂肪的摄入趋势。

支持切换查看单一指标。

当部分餐次没有对应营养数据时，保留缺失状态，统计结论注明覆盖范围。

### 10.3 记录完整度

明确区分：

- 没有记录。
- 有记录但尚未确认完整。
- 用户确认记录完整。

不将未知日期和不完整记录简单归为低摄入日。

### 10.4 简单体重管理

支持手动记录日期和体重，默认单位 kg。

提供 7 天、30 天、90 天趋势图。

用户可以补录、修改和删除历史数据。

建议默认每日期保留一条可编辑的记录，不进行自动插值或自动预测体重。

体重记录为可选功能，不要求每天填写。

---

## 11. 饮食提醒

第一版支持 Android 本地通知。

提醒功能默认关闭，由用户主动开启。

允许设置早餐、午餐、晚餐的提醒时间，并单独设置每日总结提醒。

如果当天对应餐次已经存在正式保存的记录，则跳过该餐提醒。

草稿不算已经完成记录。

系统通知权限未授予时，应明确提示提醒不可用，不影响其他功能。

不开发连续打卡奖励与排行榜。

---

## 12. 数据存储与备份

### 12.1 本地数据

保存以下信息：

- 已完成饮食记录。
- 食物及营养明细。
- 原始照片或管理后的本地照片文件。
- 用户备注与草稿。
- 本地食物及自定义食物。
- 收藏与快捷记录。
- 热量目标及历史变更。
- 体重数据。
- 提醒和外观设置。
- AI 数据来源标识。

### 12.2 完整备份

允许用户导出完整备份包。

备份包含必要的业务数据、照片、草稿、收藏及非敏感设置。

不包含 API Key、加密密钥及不必要的缓存文件。

### 12.3 可选密码加密

提供普通备份和密码加密备份。

加密备份采用适当的密码派生与认证加密机制，保证内容机密性并检测文件篡改。

恢复时需要输入正确密码。

应用不保存或上传用户设置的备份密码。

普通备份需要明确提示其中可能包含个人数据，用户应妥善保管。

### 12.4 数据恢复

通过 Android 系统文件选择器导入备份。

恢复前检查备份格式、版本、完整性和密码。

展示备份概要，并说明恢复将替换当前本地数据。

只有在校验成功、用户明确确认后才执行。

恢复失败时，不得破坏已有数据。

恢复后不自动恢复 API Key，用户需要重新配置。

### 12.5 CSV 导出

支持导出：

- 饮食记录。
- 食物明细。
- 热量及营养数据。
- 体重数据。
- 日期、餐次和数据来源。

CSV 主要用于分析，不承担完整备份恢复功能。

### 12.6 数据删除

用户可以删除单条记录、照片或全部本地业务数据。

涉及大范围删除时必须提供明确确认，并提示不可逆风险。

## 13. 核心数据一致性规则

1. 草稿不参与正式营养统计。
2. 用户覆盖的总热量优先于自动计算值。
3. 同一顿饭的总热量不得重复相加。
4. 缺失营养数据不等于零。
5. 未记录餐次不等于没有进食。
6. 历史热量目标必须与生效日期关联。
7. 本地营养库更新不得静默修改历史记录。
8. AI 重新分析不能未经确认覆盖人工修改。
9. 修改记录后应更新全部相关统计结果。
10. 所有正式记录拥有唯一标识，复制产生新记录而非覆盖原记录。
11. 体重趋势只使用实际录入的测量数据。
12. 备份恢复失败必须保证原有数据完整。

## 15. 第一版验收场景

以下场景全部应正常完成：

1. 未配置 API，手动保存一顿 850 kcal 的午餐。
2. 从外部 AI 获取结果后，手动填写并正确统计。
3. 拍照后跳过 AI，照片与记录正常保存。
4. 使用本地数据库查询米饭并通过重量计算热量。
5. AI 返回额度限制时保留草稿并允许手动完成。
6. AI 错误识别食物时允许校正。
7. 手动覆盖总热量后不与明细重复相加。
8. 缺少蛋白质信息时，不将其错误地记录为 0g。
9. 修改过去的餐次，历史和趋势图立即更新。
10. 修改每日目标后，历史目标仍然正确。
11. 当天已记录午餐时，不再发送对应的午餐提醒。
12. 不配置 API 也可以正常查看历史、图表和体重趋势。
13. 关闭应用重新打开后，记录与照片仍然存在。
14. 能够正常创建普通与密码加密备份。
15. 错误的备份密码或损坏文件不能破坏现有数据。
16. 将有效备份恢复到新安装的 App 后，业务数据与照片完整。
17. 恢复备份后 API Key 不会被自动带入。
18. CSV 文件能够正常导入表格软件进行分析。
19. 数据缺失日期不会被视为实际摄入 0 kcal。
20. 深色模式、主题切换与首次启动跳过流程正常工作。

## 16. 产品边界

第一版定位为个人饮食管理工具，不提供临床营养诊断或治疗建议。

食物热量、重量和营养素可能存在估算误差，应允许用户校正，并在数据不确定时明确提示。

软件的核心价值是便捷、稳定地保存记录，帮助用户观察趋势，而不是承诺实现特定的减重效果。
